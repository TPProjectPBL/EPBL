System Design Report v2.0 · 控制后端系统设计

隔空控制器 —— 控制后端（Control Backend）

把「眼动 + 手势」从演示级网页按钮，升级为可控制通用目标的隔空控制系统。核心是引入一个本地控制后端，接收标准化指令并通过可插拔适配器执行；第一阶段以「浏览器通用页面」为控制目标，用 Chrome DevTools Protocol（CDP）驱动，验证整条链路后再扩展到系统级控制。

文档版本 v2.0（v1.0 演进） 状态：需求确认 + 总体设计 日期 2026-11-03 第一阶段控制目标：浏览器通用页面（CDP） 信号采集：复用 dual-test 眼动 + 手势 控制后端：Python + FastAPI + Playwright

1需求确认

项目从「页面内自绘按钮的演示」升级为「通用隔空控制系统」：前端负责采集眼动 / 手势信号并输出标准化输入事件流，控制后端负责命令解释、路由与执行，通过目标适配器把指令落到具体目标上。第一阶段目标 = 浏览器通用页面（真实网页，而非自绘按键）。

1.1 与 v1.0 的定位差异（为什么要改）

维度v1.0（2026-10-17）v2.0（本次）
控制目标操作系统鼠标 / 缩放（pyautogui）浏览器通用页面（CDP / Playwright）
坐标体系屏幕像素（多屏 / 窗口定位复杂）页面视口坐标（简单、无窗口定位问题）
系统权限需 macOS「辅助功能」权限无需系统权限（仅摄像头）
架构核心「前端检测 + 后端执行」「前端采集 + 后端路由 + 适配器执行」
演进价值单一目标多目标可扩展（浏览器 → 系统 → 应用 → IoT）
核心判断：先「控制浏览器通用页面」是最低风险、最快见效的第一步——它规避了系统权限与坐标映射两大难点，同时能完整验证「信号 → 指令 → 执行」这条链路；链路跑通后，再以同一套命令模型接入系统级适配器。

1.3 非功能需求（NFR）

维度要求

跨平台浏览器控制跨平台；系统级控制（后续）以 macOS 优先、跨平台库兜底。

2可行性分析

2.1 技术可行性

关键点结论依据
眼动光标（页面内）可行dual-test 已用 WebGazer 2.1.2 + 13 点标定 + EMA + 磁吸跑通，可复用。
手势识别可行MediaPipe GestureRecognizer + 自定义 classifyHand（21 点）已跑通 6 件套。
浏览器控制可行CDP 提供 Input.dispatchMouseEvent / Input.dispatchKeyEvent / Runtime.evaluate / Page.navigate 等标准能力；Playwright 官方封装。
前端 ↔ 后端通信可行WebSocket 低延迟双向，适合连续坐标流；浏览器原生支持。
命令路由 + 适配器可行命令模型用 Pydantic 定义，适配器用接口抽象，工程成熟模式。

2.2 关键约束与难点

  • 眼动精度：普通摄像头注视点有百像素级误差，需「相对移动 + 平滑 + 死区 + 限速」，点击配合驻留或手势确认，避免误触。
  • 坐标口径统一：前端视口坐标（归一化 0–1）→ 后端换算为目标页面视口像素；需明确「谁负责换算」（约定：前端上报归一化，后端按目标视口尺寸换算）。
  • CDP 连接稳定性：Chrome 由 Playwright 托管时端口 / 生命周期需管理；连接断开要可重连、不影响前端。
  • 实时链路延迟：检测（~50ms）+ 通信（<10ms）+ 执行（<10ms）合成，目标 < 100ms；需在前端做节流（不逐帧全量上报，按 20–30Hz 采样）。
  • 跨域 / 页面类型：CDP 在页面上下文注入高亮是「浏览器特权」，不受网页跨域限制；但部分页面（如浏览器内置页、扩展页）不可控，需限定目标为普通 http/https 页面。

2.3 结论

技术路线可行，且相较 v1.0 直接控制系统鼠标，本方案的环境障碍更少（无需辅助功能权限）、坐标更简单（视口坐标）、反馈更直观（页面内可见光标 / 高亮 / 滚动）。主要风险集中在眼动精度与 CDP 连接稳定性，均可通过分步实现 + 每步验收控制。

3整体架构

采用三层解耦：信号采集层（前端）→ 控制后端（命令路由）→ 目标适配层（浏览器 / 系统 / …）。

① 信号采集层 · 前端（浏览器，复用 dual-test 能力）
摄像头采集 getUserMedia 眼动 WebGazer + 标定 手势 MediaPipe GestureRecognizer 事件生成：归一化坐标 + 手势 + 驻留 WebSocket 客户端 状态面板 UI
▲ 标准化输入事件流（JSON）· ws://127.0.0.1:8899 · 仅本地 ▼
② 控制后端 · Python 本地进程
FastAPI WebSocket 端点 Token 校验 / 心跳 命令解析 Pydantic 平滑 / 死区 / 限速 / 防抖 命令路由器 Router 状态回传
▲ 目标无关的统一 Command · 适配器接口 TargetAdapter ▼
③ 目标适配层（可插拔）
BrowserAdapter（第一阶段）
Playwright / CDP → 光标·点击·滚动·导航·高亮 SystemAdapter（后续）
pyautogui → 系统鼠标·缩放 AppAdapter（后续）
应用 API / 快捷键 IoTAdapter（后续）
第一阶段仅实现 BrowserAdapter；其余为预留接口，验证可插拔性即可。

3.1 数据流

  1. 前端取帧 → 眼动检测生成注视点、手势检测生成手势状态。
  2. 前端将结果封装为标准化输入事件（光标归一化坐标 / 手势名与状态 / 驻留点击），按 ~20–30Hz 经 WebSocket 上报后端。
  3. 后端校验 token，解析命令，做平滑 / 死区 / 限速，路由给当前激活的目标适配器。
  4. BrowserAdapter 将命令翻译为 CDP 调用（移动 / 点击 / 滚动 / 导航 / 注入高亮），作用于目标页面。
  5. 后端把执行结果与状态（连接、目标、缩放级别、错误）回传前端展示。

3.2 命令模型（协议草案）

// 前端 → 后端：输入事件流
{ "type": "cursor",  "x": 0.52, "y": 0.31, "ts": 1730620000000 }
{ "type": "gesture", "name": "scroll_up", "state": "start" | "hold" | "end" }
{ "type": "dwell",   "x": 0.52, "y": 0.31 }                 // 驻留点击（可选）

// 后端 → 前端：状态回传
{ "type": "state",   "target": "browser", "connected": true, "page": "https://..." }
{ "type": "highlight", "x": 0.52, "y": 0.31 }               // 页面内高亮反馈
口径约定：前端只上报归一化坐标（0–1）与语义手势名；换算为目标视口像素、以及手势→动作的映射，全部由后端负责。这样前端不变，扩展新目标只改后端适配器。

5技术选型与理由

技术项选型选型理由
眼动追踪WebGazer 2.1.2（本地 vendor + facemesh 模型）已在 dual-test 跑通、离线可跑、有 13 点标定，零迁移成本。
手势识别MediaPipe GestureRecognizer + 自定义 classifyHand21 点判定 6 件套手势已定稿且可靠，复用现有实现。
前端 ↔ 后端通信WebSocket（原生）低延迟双向、连续坐标流场景合适、无额外依赖。
后端框架Python 3.11 + FastAPI + uvicorn异步高并发、WebSocket 支持好；延续 v1.0 技术栈，减少切换成本。
命令校验Pydantic v2类型安全、校验 + 序列化一体，命令模型稳定可靠。
浏览器控制Playwright（Python）官方 Python 支持、封装 CDP 成熟、可托管启动 Chrome、元素级操作与 JS 注入齐全。
测试pytest + websockets（客户端）+ Playwright 断言后端接口可测、浏览器行为可自动断言。
为何第一阶段选 Python 而非 Node：① 延续 v1.0 已定的 Python 后端方向，降低切换成本；② Playwright 对 Python 与 Node 支持同等完善，能力无短板；③ 为后续「系统级控制（pyautogui）」留同一语言栈，避免前后两阶段语言割裂。

6风险点与应对

风险影响应对
眼动精度不足 / 抖动光标漂移、难对准、误触相对移动 + EMA 平滑 + 死区 + 限速；点击配合驻留或手势确认。
CDP / Chrome 连接不稳定控制中断Playwright 托管生命周期；断连自动重连；状态面板显式提示。
坐标口径不一致光标 / 点击错位约定前端只报归一化坐标，后端统一换算；单测覆盖坐标换算。
页面类型不可控部分页面无法控制限定目标为普通 http/https 页面；内置页 / 扩展页明确排除。
高频上报导致延迟 / 卡顿链路延迟超标前端按 20–30Hz 节流采样；后端限速。
隐私顾虑用户拒绝摄像头全程本地处理、不上传不落盘；明示隐私边界。
多目标切换混淆指令发错目标路由层单一「激活适配器」；状态面板展示当前目标。

7可扩展性

  • 新控制目标：实现新的 TargetAdapter（系统 / 应用 / IoT）即可接入，命令模型与前端不变。
  • 新手势 / 动作：手势集与「手势→动作」映射集中在后端路由层配置，新增手势不改前端核心。
  • 检测下沉后端：后续可把 MediaPipe 移到后端（Python mediapipe + opencv），前端退化为纯展示 / 遥控，复用同一命令协议。
  • 参数化配置：灵敏度、死区、平滑系数、手势阈值、点击驻留时长集中配置，支持热更新。
  • 元素级智能：BrowserAdapter 后续可加「注入 JS 查 DOM → 语义化点击」，从坐标点击升级到元素点击。
  • 多浏览器 / 多页面：Playwright 支持 Chromium / Firefox / WebKit，可扩展到多目标页面。

8安全性

  • 本地闭环：后端仅监听 127.0.0.1，不接受外部网络连接，防止远程控制。
  • 认证：WebSocket 连接带一次性 token（后端启动时生成，仅回显给前端），避免其他本地进程误连。
  • 数据本地化：摄像头画面与生物特征仅在本地处理，不上传、不落盘。
  • 最小权限：第一阶段仅需摄像头权限；无需系统辅助功能 / 输入监控等敏感权限。
  • CDP 隔离：Chrome 由 Playwright 以独立用户数据目录启动（`--user-data-dir` 临时目录），不与用户日常浏览器共享会话与登录态，避免污染或泄露。
  • 命令白名单：后端只接受命令模型内定义的动作，非法类型 / 越界坐标直接拒绝。

9实现步骤与验收

采用「后端先行（可独立用脚本驱动）→ 前端接入 → 端到端联调」的分步推进，每步独立可测、可验收。

步骤 1 · 命令协议 + 后端骨架

FastAPI WebSocket 端点、Pydantic 命令模型、Token 校验、心跳、TargetAdapter 接口与空实现、统一 Command 定义。

测试：pytest 校验命令模型（合法 / 非法 / 越界）；用测试客户端连上 WebSocket 做心跳与命令往返。
验收：后端可启动、仅监听 127.0.0.1；非法命令被拒绝；心跳正常；连接断开可重连。

步骤 2 · BrowserAdapter（Playwright / CDP）

Playwright 托管启动 Chrome（独立 user-data-dir），实现移动光标、点击、滚动、导航、元素高亮（Runtime.evaluate 注入覆盖层）。

测试：写脚本向后端发固定 Command，观察浏览器页面光标移动 / 滚动 / 点击 / 导航 / 高亮；Playwright 断言页面变化。
验收：后端能启动并控制 Chrome；滚动 / 点击 / 导航生效；高亮出现在指定视口坐标；断连可重连。

步骤 3 · 前端信号采集模块化

从 dual-test 抽出眼动 + 手势，封装为「事件生成器」，输出归一化坐标 + 手势名 + 驻留，按 20–30Hz 经 WebSocket 上报，加自动重连。

测试：前端日志观察事件流；手动断开后端看自动重连；状态面板显示连接态。
验收：前端稳定输出标准化事件；WebSocket 断线自动重连；状态面板正确反映检测 / 连接 / 目标。

步骤 4 · 前后端联调（视线 → 浏览器光标 / 滚动）

前端上报归一化坐标，后端换算为页面视口像素，驱动浏览器内光标移动；手势映射滚动。

测试：转动眼球，观察浏览器页面光标随视线移动、页面滚动；对照前端「视线光标」与浏览器光标。
验收：端到端增量延迟 < 100 ms；移动方向与视线一致；死区与限速生效无抖动；滚动方向正确且连续。

步骤 5 · 通用测试页 + 点击 / 导航 / 完整手势映射

提供通用测试页（按钮 / 链接 / 长滚动区 / 输入框 / 翻页）；接入驻留点击；6 件套手势映射到返回 / 主页 / 菜单 / 上滚 / 下滚 / 确认。

测试：眼动 + 手势完整操控测试页走查（点按钮、点链接跳转、滚动长页、翻页、返回）。
验收：真实用户操作可用；点击准确（配合驻留 / 手势确认）；手势误触可控；状态面板全程反馈。

步骤 6 · 稳健性与安全加固

异常降级（无脸 / 无手 / 低置信度提示）、限速、token、独立 Chrome 会话、日志与指标。

测试：遮挡镜头、移开手、拔断连接、重启后端等异常场景逐一验证。
验收：所有异常均有明确反馈与降级，不崩溃；后端不监听外部网络；Chrome 会话隔离生效。

步骤 7 · 端到端验收

全链路联调：眼动 + 手势同时运行，以通用测试页为靶场完整走查，测性能与稳定性。

测试：真实用户盲测 + 性能记录（延迟 / 帧率 / 误触率）。
验收：达到第 10 章 KPI；链路稳定运行 ≥ 5 分钟无崩溃；异常场景均降级。
