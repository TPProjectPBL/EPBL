执行摘要

一屏看懂结论

现状是一组各自独立、可直接用 HTTP 静态服务打开的演示页：眼动/手势测试台、控制前端、 手势精度测试、隔空画板、眼动翻页、受控靶场等。它们共享 WebGazer、MediaPipe 与本地 vendor 资源，但缺少统一入口、统一导航、统一版本与分发方式；「控制小窗」目前只有 launcher_cocoa.py 脚本，还没有 DMG。

核心结论
技术上完全可行，但需分两段交付。 ① 工作台（侧栏 + iframe 集成 + 下载中心）用「纯静态单页 + 本地服务守护」实现，零构建、可离线、 与现有页面同源，2–3 人日即可跑通； ② DMG 分发是有条件可行——用 py2app 打包「控制小窗」GUI、Playwright/Chromium 走首次引导安装、 hdiutil 生成 DMG + ad-hoc 签名，需额外处理 Gatekeeper 与体积问题（约 4–6 人日）。
最大风险（必须前置决策）
摄像头 API 只在 localhost/https 可用，因此工作台不能以 file:// 打开； 同时 WebGazer/MediaPipe 各自持有摄像头，多个模块不能同时占用摄像头。这两点决定了架构必须包含 「本地服务守护」与「单实例摄像头互斥」两个强制设计。

关键设计决策（TL;DR）

决策点选择一句话理由
工作台形态纯静态单文件 + 原生 JS零构建、可离线、与现有纯静态页同构，最快落地
模块集成iframe 懒加载 + 单实例互斥业务页零改造，天然隔离，切换即销毁以释放摄像头
服务托管复用 Python http.server :8125已有实现，避免引入 nginx/Node 依赖
DMG 打包py2app + hdiutil + ad-hoc 签名能打包 pyobjc 原生小窗、体积可控，Playwright 首次安装
配置驱动modules.json 注册表新增页面零改代码，扩展成本最低

需求确认

先把「做什么」钉死，再谈怎么做

1.1 一句话目标

交付一个统一的本地 Web 工作台：左侧栏列出仓库所有可用界面，点击即在右侧加载对应页面； 工作台内提供「控制小窗」DMG 下载及安装说明，让非开发用户双击安装即可使用。

1.5 验收总口径

  1. 可用：任意 macOS 机器上，双击 DMG 安装后，能打开工作台并切换至少 5 个模块。
  2. 不冲突：模块之间切换不会触发摄像头占用冲突；切走后摄像头指示灯熄灭。
  3. 可分发：DMG 含版本号与 SHA-256，安装指引覆盖「已签名」与「未签名」两种情况。
  4. 可扩展：新增一个模块只需在 modules.json 增加一条记录。

03

可行性分析

哪些能做、哪些有条件、哪些不做

3.1 工作台整合：可行（低风险）

这些页面都是静态 HTML，且大多以相对路径引用本地 vendor，天然适合同源静态托管。 侧栏 + iframe 属于浏览器原生能力，不需要框架。唯一硬约束是必须经 HTTP 访问（摄像头权限）， 由现有 http.server 8125 满足。

3.2 DMG 分发：有条件可行（中高风险）

「网页里给出 DMG 下载」本身简单（放链接 + 校验和），难点在于如何产出 DMG。三种打包路线对比：

路线能打包什么体积难点结论
py2app pyobjc 原生小窗 launcher_cocoa.py ~20–40MB uvicorn/playwright 依赖需作为 resource 或首次安装；universal2 困难 推荐 v1
PyInstaller Python 全依赖（含后端） ~100–200MB Playwright Chromium 仍需单独下载；启动慢；路径/权限 备选
Tauri/Electron 壳 Web 工作台 + 内置服务 ~60–150MB 引入新工具链；需 Rust/Node；摄像头权限与 CSP 配置 v2 再议
DMG 的真实成本在「首次运行」
Playwright 的 Chromium 约 150MB+，且版本与 playwright==1.60.0 强绑定，不适合塞进 DMG。 推荐：DMG 只装「控制小窗 + 静态服务」，首次启动时检测并引导执行 playwright install chromium；失败时给出可复制的命令与诊断日志。

3.3 权限可行性

约束事实设计应对
getUserMedia 安全上下文仅 https 或 localhost 可用，file:// 不可强制经 8125 本地服务；DMG 的 .app 负责拉起服务
iframe 摄像头需 allow="camera"，且父页与子页同源更稳全部同源 + 显式 allow 白名单
macOS 系统权限首次请求弹窗，需用户在「系统设置 → 隐私 → 摄像头」允许安装指引 + 页内引导文案
Gatekeeper未签名/未公证的 DMG 打开 .app 会被拦ad-hoc 签名 + 「右键 → 打开」指引；v2 申请开发者签名

3.4 性能可行性

  • WebGazer（TF.js）与 MediaPipe Vision（wasm/GPU）都会吃 CPU/GPU；同时只跑一个模块可避免叠加。
  • 1080p 采集已在本仓库落地；iframe 内与顶层页性能一致。
  • 懒加载 + 切走销毁可保证长会话不累积内存。

3.5 合规与隐私可行性

生物特征（人脸/视线）属敏感数据。现状已在本地处理、不上传；工作台需在 UI 明示「画面仅本地处理」， 结果导出仅数值，符合当前红线。公开仓库不得提交录制/照片（CONTRIBUTING.md 已规定）。

3.6 结论矩阵

能力结论前提
侧栏工作台 + 11 页整合可行经 8125 HTTP 访问
摄像头单实例互斥可行切换时销毁 iframe
DMG 下载入口可行需先产出 DMG 产物
DMG 内置完整后端不推荐体积/版本/权限成本高
DMG 内置小窗 + 首次装后端推荐需网络；需失败诊断
公证分发v2需 Apple Developer 账号

4.3 关键交互时序（切换模块）

用户点击侧栏模块 A
  → 工作台：若当前有激活 iframe，先 iframe.remove()（触发页面卸载 → getUserMedia 轨道停止）
  → 工作台：创建新 <iframe src=模块A allow="camera; microphone; fullscreen; autoplay">
  → 模块A 启动 WebGazer / MediaPipe → 请求摄像头 → 系统权限（首次）
  → 模块A 可选：WS 连接 ws://127.0.0.1:8899/ws?token=… → 上报/接收指令
为什么必须销毁 iframe
仅设置 display:none 不会停止摄像头与预测循环，反而会持续占用并拖慢性能； iframe.remove() 会卸载文档、释放媒体轨道，是最可靠的「单实例」实现方式。

6.2 关键理由展开

① 为什么不用 React/Vite？

工作台本质是「导航 + 一个 iframe + 一个下载卡片」，状态极少。引入构建链会带来 Node 依赖、产物目录、 部署差异，而当前仓库刻意保持纯静态（CONTRIBUTING.md 明确所有 demo 直接起 http 服务）。 用原生 JS 约 200–300 行即可完成，且能被现有 DMG/服务直接托管。

② 为什么用 iframe 而不是把页面改造成组件？

11 个模块由不同作者、不同技术（WebGazer / MediaPipe CDN / 纯 DOM）实现，且依赖各自的相对资源路径。 改成组件等于重写并重测全部模块；iframe 保持它们原样、独立演进，工作台只负责装载与生命周期。 同时 iframe 的卸载语义天然解决摄像头占用问题。

③ 为什么 Playwright/Chromium 不进 DMG？

Chromium 与 playwright==1.60.0 版本强绑定、体积 150MB+，且安装路径与运行时校验复杂。 放进 DMG 会让体积翻数倍、构建矩阵膨胀。改为「首次运行引导安装」，失败时给出可复制命令与日志， 回收体积与维护成本。

④ 为什么 v1 用 ad-hoc 签名？

Apple Developer 账号与公证流程需要申请与等待。ad-hoc（codesign -s -）可让 .app 在本机通过 Gatekeeper 的完整性检查（仍需「右键 → 打开」首次放行），足够内测分发；v2 再切 Developer ID + 公证。

⑤ 为什么注册表用 JSON？

模块的增删改本质是数据变更。JSON 让非前端成员也能维护入口，并可直接由脚本校验路径存在性 （见附录 E 的验收脚本），把「文档」变成「可执行约束」。

安全性设计

网络面、隐私、前端隔离、分发链、供应链

9.1 网络面

  • 所有服务只绑定 127.0.0.1，不监听 0.0.0.0。
  • WebSocket 必须带 token：现状 AC_TOKEN 默认 air-controller-dev；建议启动时随机生成并注入，不写日志、不入库。
  • 后端仅暴露必要端点（/health、/ws、/camera），不开放文件写入/命令执行。

9.2 摄像头与隐私

  • 视频帧仅在本机内存处理；不录制、不上传、不落盘。
  • 导出结果仅含数值（偏差、命中率、混淆矩阵），不含图像。
  • 工作台与各模块显著位置提示「画面仅本地处理」。

9.3 前端隔离

措施配置说明
CSPdefault-src 'self'; media-src 'self' blob:; connect-src 'self' ws://127.0.0.1:8899限制外链与内联执行
iframe 权限allow="camera; microphone; fullscreen; autoplay"仅授予模块所需能力
iframe sandbox使用 allow-scripts allow-same-origin，不加 allow-top-navigation防止模块劫持顶层导航
外链提示external 模块用 rel="noopener noreferrer"防止窗口引用泄露

9.4 分发链

  • DMG 产物旁提供 .sha256，下载中心展示校验和。
  • 构建脚本 codesign --verify --deep --strict 自检后再出包。
  • 版本号写入 Info.plist 与 releases.json，安装指引说明如何核对。

9.5 供应链

  • requirements.txt 已锁定版本；升级需单独 PR + 回归。
  • vendor 第三方库记录来源与版本（WebGazer 2.1.2 patched、MediaPipe Vision）。
  • 禁止提交私钥/证书（.deepworks/tmp/ssl 已在 gitignore 范围，需在文档强调）。

codesign --force --deep --sign - "dist/隔空控制器.app"

# 3) 生成 DMG
hdiutil create -volname "隔空控制器" -srcfolder "dist/隔空控制器.app" \

# 4) 校验和
shasum -a 256 "dist/隔空控制器-v1.0.0-arm64.dmg" | tee "dist/隔空控制器-v1.0.0-arm64.dmg.sha256"
