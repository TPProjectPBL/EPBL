## 0. 一句话定位（v0.3）

以 **Web App** 为主形态的**通用方向翻页交互产品**，用 **上 / 下 / 左 / 右** 方向操作替代传统翻页按键，**不对目标场景做单一收敛**（演示讲课 / 阅读 / 无障碍三场景共用同一方向翻页核心），并作为已有《手机端视线估计与无感自适应校准》项目的下游交互应用形态。

> 与 v0.2 的变化：后端定档位 0（无后端起步）；用户面按你的决定**暂不收敛**，建议以"场景中立、只做共用核心"的方式降低风险（见第 6.2 节）。

## 2. 已拍板决策

1. **主形态 = Web App**（已确认，不再在"插件 / 网站"间摇摆）。
2. **核心交互 = 方向翻页**，首发限定 上 / 下 / 左 / 右。
3. **与已有眼动项目的关系 = A（同一项目的不同阶段）**：眼动 / 视线是输入手段，"方向翻页"是其交互输出形态之一。
4. **后端 = 档位 0（无后端起步）**：纯静态托管 + 浏览器本地状态，成本 0；将来需要"手机→大屏遥控"再升级到档位 1。
5. **用户面 = 暂不收敛**：演示 / 阅读 / 无障碍三场景并列保留，首发只做三者共用的方向翻页核心（执行方式见第 6.2 节）。
6. **成本策略 = 免费优先 + 小额支出**。
7. **目标节点 = 12 月初**。

## 5. 后端职责建议（回答"后端到底干什么"）

### 5.1 结论先行（**已拍板：采用档位 0**）

**MVP 阶段：后端"能不要就不要"——已决定采用档位 0，无后端起步。** 只有当将来要做"手机遥控大屏"时，才需要升级到**只转发指令的极简信令服务（档位 1）**。

后端**永远不接收视频帧或人脸数据**——这是已有项目的隐私红线（"原始人脸帧不出设备"），必须继承。

### 5.2 三档方案

| 档位 | 何时需要 | 后端实际职责 | 技术选型 | 成本 |
|---|---|---|---|---|
| **档位 0（推荐 MVP）** | 翻页只作用于本机页面 | **无后端**：纯静态托管 + 本机状态 | Cloudflare Pages / Vercel / GitHub Pages | **0 元** |
| **档位 1（演示场景核心）** | 手机当遥控器 → 控制大屏 / 投影 | 只做 3 件事：① 创建 / 加入房间 ② 广播翻页指令（up/down/left/right）③ 心跳与断线清理 | WebSocket：Cloudflare Durable Objects / PartyKit / Supabase Realtime / Firebase | 免费额度内 |
| **档位 2（MVP 不做）** | 登录、收藏、跨设备历史、统计 | 用户 / 数据持久化 | Supabase 等 BaaS | 免费额度内 |

### 5.3 关键约束（写入架构红线）

1. **指令级，不是像素级**：后端只传"翻上一页 / 下一页"这类指令，**不传画面、不传人脸、不传视频流**。
2. **眼动推理必须在端侧**：若将来接入眼动，推理发生在浏览器内（WASM / WebGPU / ONNX Runtime Web）或手机端侧模型，本地算出指令后再上报。
3. **状态可无服务**：翻页进度、历史保存在浏览器 `localStorage`，不依赖账号体系。
4. **免费优先**：静态托管 + Serverless / 免费额度的实时服务，避免固定服务器开支。

### 5.4 为什么不是"更重的后端"

- Q9 明确不新增 AI，后端没有模型服务的必要性；
- Q5 的核心是"低延迟稳定"，**链路越短延迟越低**，静态托管反而是最优解；
- Q8 要求免费优先，重后端直接违背预算约束。

## 6. 目标用户：评估与执行方式（**已定：暂不收敛**）

### 6.1 三个候选场景横向评估

| 场景 | 痛点强度 | 现有方案强弱（Q3） | 与已有眼动项目契合度 | 首发 6.5 周可行性 |
|---|---|---|---|---|
| **演示 / 讲课** | **强**：翻页笔要另购、易丢、要换电池、跨软件兼容差 | 中（硬件为主，无软件通用方案） | **高**（与"隔空画画"现场 Demo 调性一致） | **高** |
| 阅读电子书 / 漫画 | 中：自带手势翻页已基本够用 | **强（红海）**：阅读器与漫画 App 自带体验成熟 | 中 | 高但**差异化最弱** |
| 无障碍 / 大屏 | **强**：真实刚需 | 弱 | **高** | **低**（合规、安全、验收门槛高） |

### 6.2 你的决定：**暂不收敛（三场景并列保留）**

已确认**不把目标场景收敛到单一方向**。为控制风险，建议采用"**场景中立、只做共用核心**"的执行方式：

| 做法 | 说明 |
|---|---|
| 只做三场景共用能力 | 方向翻页、低延迟、稳定、通用宿主——不为任何单一场景做专属功能 |
| 不做场景专属定制 | 首发**不做**"演讲者视图""漫画连续滚动""无障碍专属热区"这类特化功能 |
| 用真实反馈再定向 | 上线后按实际使用数据与用户反馈，再决定把资源投向哪个场景 |

> 风险提示：三场景不收敛会让定位叙事偏散、首发验收缺少唯一焦点。上面的"场景中立"方式是在不砍场景前提下最稳的走法。

### 6.3 评估参考（原推荐结论，**未被采纳**）

1. **演示场景的痛点最锐利且可量化**：翻页笔是"要花钱买、会丢、会没电、换台电脑就不好用"的物理痛点。
2. **与已有项目天然契合**：眼动项目对外就是"零穿戴、隔空操作"的现场体验，演示 / 讲课是同一套叙事的自然延伸。
3. **阅读场景是红海**：Q3 列出的三类现成方案里有两类都属于它，首发切进去最难建立差异。
4. **无障碍场景价值高但门槛高**：涉及合规与安全验收，不适合 6.5 周快跑。

### 6.4 重要联动

> **若将来把主场景定为"演示 / 讲课"，后端档位 1（手机→大屏遥控）会从"可选"升级为"接近必需"**——因为"用手机替代翻页笔"才是这个场景的核心价值。**当前场景暂不收敛，故档位 1 暂缓（P2）**；一旦收敛到演示场景，请在 1 周内启动信令服务选型验证。

## 8. 预算与技术约束

- **必须免费可用**：开发工具链、代码托管、静态部署。
- **可接受小额支出**：域名、以及档位 1 超出免费额度后的实时服务费用。
- **不建议**：MVP 阶段引入付费重资产（商用授权、付费模型服务、固定服务器）。
- **推论**：架构应"静态优先 + Serverless 兜底"，把后端职责压到通信指令级。
